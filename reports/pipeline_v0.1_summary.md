# AAOCA text pipeline v0.1 — actual run summary

Run date: 2026-09-25. Final output: `data/derived/v0.1_full/`. This report contains aggregate results only. Source PDFs, patient linkage, extracted text and OCR stay in restricted local storage. No patient content was sent to an external API, and no LLM was used.

## 1. Dataset reality

The cleaned cohort CSV has **232 patient rows**. All 232 have a nonempty six-digit inpatient ID and an outpatient ID; inpatient IDs and names are unique. Outpatient IDs have 231 unique values because two distinct patients share one non-placeholder outpatient ID. That conflict is retained and resolved only when the unique inpatient ID is available.

The configured roots contain **365 PDF paths**: 342 distinct SHA256 contents plus 23 exact duplicate copies. Every file in `data/sample_raw` is a byte-identical copy of a file in the hospital source directory. The 342 unique contents comprise **232 medical-record bundles** and **110 laboratory bundles**, totaling **13,485 pages**. These are webpage-print bundles: one PDF commonly contains many clinical documents, and one laboratory page can contain multiple reports.

Patient association is not completely determined by filenames. Exact filenames initially cover most files; three files with filename/name differences are recovered through exact hospital export URL identifiers. The final run associates **341/342 unique PDFs** with **231/232 cohort patients**. One PDF contains identifiers absent from the cohort and remains unmatched; one cohort patient has no PDF in the configured scope. The cohort also contains one shared outpatient ID, 13 documents whose internal historical/truncated ID differs from the stable export URL, and six PDFs whose header outpatient ID differs from the CSV. These discrepancies are preserved as QC evidence, never silently corrected.

The PDF generator determines text quality. All **198 PDFs with unusable Chinese text layers** were generated by Chrome Helper/macOS Quartz; all **142 clean text-layer PDFs** were generated by Safari/macOS Quartz. In the former, visible Chinese is stored as vector paths, while remaining digits/Latin text can still be extracted. There is no hidden Chinese layer, usable CMap, `ActualText`, or structure tag to restore the prose. One additional PDF is partial and one is an empty/zero-page PDF.

## 2. Pipeline implemented

The runnable package implements the complete v0.1 path:

1. Load every CSV row as strings, retain source identifiers locally, create stable pseudonymous patient IDs, and report duplicate/conflicting identifiers.
2. Recursively scan configured PDF roots, hash every readable file, preserve every source path, identify exact duplicates, and match using exact filename plus stable header URL evidence. Fuzzy names and arbitrary body-number searches are not used.
3. Extract the native PDF text layer page by page with PyMuPDF, including text outside the nominal MediaBox. Record page count, raw characters, CJK count, coordinates, paint diagnostics, flags, success status and OCR recommendation. Parser exceptions have a pypdf fallback.
4. Apply local PP-OCR v6 only to pages flagged as missing/unusable/mixed text. Keep OCR text, line polygons, confidence and model provenance separate from raw PDF text. Atomic SHA/model-version caches make long OCR runs resumable.
5. Normalize the selected analysis representation with NFKC, whitespace cleanup and a conservative browser-chrome allowlist. Preserve raw text, OCR text, page boundaries, normalized-line maps and every removed line/reason.
6. Split bundled PDFs with observed title/date/laboratory templates. Preserve unknown preambles and damaged continuations, page/line/character spans, exact section text, section type, date evidence, mentioned dates, date precision and uncertainty.
7. Generate patient, document, page and section indexes plus a patient timeline. Exact duplicate copies remain in the document inventory but contribute sections/timeline only once.
8. Generate automated QC for matching, missing patients/files, parse status, empty/tiny pages, duplicates, unknown type/date, OCR queue/results, date review, line coverage and source integrity.
9. Export conservative date-only cutoff subsets while excluding same-day, unknown/uncertain dates and unreviewed OCR dates. The receipt explicitly states that event-date filtering alone is not leakage-free because `available_at` remains unknown.
10. Provide a future local enrichment adapter contract with evidence references, method version and assertion status. v0.1 does not load or call an LLM and does not automatically infer clinical management.

## 4. Failure cases

1. **Vector-outlined Chinese:** 198 PDFs have visible Chinese but no usable Chinese text layer. They require local OCR unless the hospital pages can be re-exported through a browser that preserves fonts.
2. **Residual OCR empties:** 14 recommended pages still yield no OCR text. They remain visibly flagged and are not upgraded to success.
3. **Dense laboratory tables:** 2,643 OCR pages contain low-confidence lines. v0.1 preserves geometry but does not claim that analyte, result, unit and reference range have been paired correctly.
4. **Unknown dates:** 3,509 sections have no reliable document date, including 2,697 administrative sections. Signature, admission, sample-submission, print and planned-operation dates are deliberately not substituted.
5. **Date conflicts:** 35 sections have conflicting document dates, 27 laboratory sections have conflicting test dates, and one section has different same-day times. Conflicting days remain unknown; conflicting same-day times retain only day precision.
6. **Unknown document type:** 367 sections do not match a stable observed title/template. They remain accessible with exact evidence spans.
7. **Identity discrepancies:** one PDF is outside the cohort, one cohort patient lacks a PDF, one outpatient ID is shared, and header/internal IDs disagree in a small set. Original evidence is retained for reconciliation.
8. **Print-layout artifacts:** 132 PDFs contain off-page text, affecting 2,602 pages. The extractor recovers it, but visibility and intended reading order cannot be inferred solely from coordinates.
9. **One empty PDF:** one medical-record source has zero pages/content and cannot yield sections or a timeline.
10. **Leakage-sensitive narrative:** 4,241 sections contain postoperative/treatment wording and 1,033 sections have an outcome-information warning. Document dates do not prove when information became available to a prediction model.

- `section_index.csv`: section type/date/provenance/page spans/text references;

- `date_mentions.csv`: document-date and content-mentioned dates kept separately;

- `normalized/*.json` and `*.txt`: raw/OCR/normalized representations and page boundaries;
- `sections/*.json`: full section text, evidence, mentioned dates and exact spans;
- `qc/*.csv` and `cohort_summary.json`: automated QC and aggregate counts;
- `private/patient_linkage.csv` and `private/document_matching_evidence.csv`: restricted direct-identifier linkage/evidence;
- `source_inventory.csv`: input SHA256 and post-run unchanged verification;
- `run_metadata.json` and `logs/pipeline.log`: configuration, code/model versions, receipt and execution log;
- `cutoffs/before_2024-01-01.csv` plus receipt: an executed cutoff-interface test containing 2,191 native/reviewed events strictly before that day. It is explicitly not certified leakage-free.

Intermediate text-only and probe iterations remain under `data/derived/iteration_*` for audit. They are development evidence and their older counts must not be used as final results.

## 6. Remaining uncertainties

- OCR and section/date rules have not been compared with a clinician-reviewed gold set. Passing structural checks proves traceability and internal consistency, not medical transcription accuracy.
- OCR-derived dates and section boundaries remain unreviewed. Their model confidence is not calibrated for this hospital export.
- Laboratory report dates come from the observed `检验时间` column; this may be specimen/result time rather than report signing or availability time.
- `available_at` is unknown. A retrospective document can mention later outcomes even when it carries an earlier clinical event date.
- `surgery_related` groups planning, consent, discussion, operation and postoperative documents. It is not evidence that surgery was actually completed.
- Ultrasound/follow-up may be embedded within narrative or OCR text, but no sufficiently stable standalone template was added in v0.1.
- The unmatched PDF, missing-patient PDF coverage and identifier discrepancies require reconciliation with the hospital/cohort owner.
- Phase I clinical fields (`aaoca_status`, `observed_management`) were deliberately not generated. The base pipeline is now runnable, but actual surgery labeling needs assertion-state rules and reviewed evidence.

## 7. Recommended next iteration

1. Build a stratified, clinician-reviewed reference set covering native/OCR medical records, native/OCR laboratory pages, section boundaries, document dates and difficult tables. Measure transcription, boundary/type and date accuracy separately.
2. Reconcile the unmatched PDF, the patient without a PDF, the shared outpatient ID and header/CSV discrepancies with the data provider; do not resolve them algorithmically from clinical prose.
3. Add geometry-aware laboratory table reconstruction and validate analyte/result/unit/reference-range relationships against annotated pages before exposing row-level lab data.
4. Define `available_at`, index decision time and clinical stage rules for prediction cutoffs. Review every outcome/leakage flag before any surgery-versus-conservative modeling dataset is built.
5. Add a small evidence-first clinical extraction prototype: distinguish recommendation, plan, consideration and completed procedure; write `observed_management=surgery` only from explicit completion evidence, with page/text reference and review status.
